WHAT DOES "DATABASE & DOCKER PERSISTENCE" MEAN IN SPRING BOOT?
SPRING BOOT'TA "VERİTABANI KALICILIĞI, PROFILLER VE DOCKER COMPOSE" NE ANLAMA GELİR?
================================================================================

1. GENEL ANLAMI VE HEDEF:
--------------------------------------------------------------------------------
Spring Boot uygulamalarında geliştirme aşamasında geçici (In-Memory H2) veritabanı
kullanılırken, üretim (Production) ve portföy seviyesinde kalıcı, ölçeklenebilir ve 
endüstri standardı bir veritabanı (PostgreSQL) gereklidir.

Adım 1 kapsamında projeye:
1. PostgreSQL 16 Driver bağımlılığı (`org.postgresql:postgresql`) eklendi.
2. Çift Profil Desteği (`dev` vs `postgres`) kuruldu.
3. Docker Compose ile PostgreSQL servisi, Kalıcı Hacim (Volume) ve Sağlık Kontrolü (Healthcheck) yapılandırıldı.
4. Hibernate PostgreSQL Dialect ve HikariCP Bağlantı Havuzu (Connection Pool) optimize edildi.


2. PROFİL YAPISI VE ÇALIŞMA MANTIĞI:
--------------------------------------------------------------------------------
Spring Boot profilleri, uygulamanın farklı ortamlarda farklı ayarlarla çalışmasını sağlar:

A) DEV PROFİLİ (`application-dev.properties`):
   - Hızlı yerel geliştirme ve offline testler içindir.
   - Bilgisayarda Docker veya PostgreSQL kurulu/açık olmasa bile uygulama anında ayağa kalkar.
   - H2 veritabanını kullanır (`database_memory_persist/blog`).
   - H2 Web Konsolu aktiftir: `http://localhost:5555/h2-console`

B) POSTGRES PROFİLİ (`application-postgres.properties`):
   - Kurumsal ve kalıcı veritabanı katmanıdır.
   - PostgreSQL 16 ile çalışır.
   - Bağlantı parametreleri:
     * URL: jdbc:postgresql://localhost:5432/blog_db (Docker içinde: jdbc:postgresql://postgres:5432/blog_db)
     * Kullanıcı Adı: postgres
     * Şifre: root
     * Havuz (HikariCP): Maximum 10 bağlantı, 5 idle bağlantı.
     * DDL-Auto: update (Tabloları entity sınıflarına göre otomatik günceller, veriyi silmez).

C) TEST PROFİLİ (`src/test/resources/application.properties`):
   - Birim ve entegrasyon testlerinde hızlı in-memory H2 kullanır; testler dış ortama bağımlı olmadan izole çalışır.


3. DOCKER COMPOSE MİMARİSİ (`docker-compose.yml`):
--------------------------------------------------------------------------------
+---------------------------+       +-----------------------------+
|    container_blog_backend | ----> |   container_blog_postgres   |
|     (Spring Boot - 5555)  |       |     (PostgreSQL 16 - 5432)  |
+---------------------------+       +-----------------------------+
              |                                    |
     [./upload (Disk)]                 [springboot2026_postgres_data]
   (Blog Kapak Görselleri)                  (Veritabanı Tabloları)

Önemli Özellikler:
- Healthcheck (Sağlık Kontrolü): `pg_isready` komutu ile veritabanı hazır olmadan backend ayağa kalkmaz (`depends_on.condition: service_healthy`).
- Named Volume (`springboot2026_postgres_data`): Container'lar silinse veya güncellense dahi veritabanı tabloları ve kayıtları asla kaybolmaz.
- Redis Servisi (`container_blog_redis`): Redis 7 Alpine imajı, 6379 portu, `springboot2026_redis_data` volume'ü ve `redis-cli ping` sağlık kontrolü ile çalışır.
- Prometheus Servisi (`container_blog_prometheus`): Prometheus imajı, 9090 portu, `prometheus.yml` yapılandırması ve `springboot2026_prometheus_data` volume'ü ile backend metriklerini (`/actuator/prometheus`) periyodik toplar.
- Grafana Servisi (`container_blog_grafana`): Grafana imajı, 3001:3000 portu, otomatik Prometheus datasource provisioning ve `springboot2026_grafana_data` volume'ü ile CPU/RAM/JVM/Hikari/HTTP panellerini görselleştirir (admin/admin).
- Docker Network (`fullstack_network`): Backend, Postgres servisine (`postgres:5432`), Redis servisine (`redis:6379`), Prometheus ve Grafana sistemlerine doğrudan container adıyla erişir.


4. REDIS CACHE MİMARİSİ (Adım 4):
--------------------------------------------------------------------------------
Sık okunan ve nadir değişen veriler (Kategoriler, Etiketler) veritabanına her istekte
tekrar tekrar yük bindirmesin diye Redis önbellek (Cache) katmanı ile hızlandırılmıştır:

1) @Cacheable:
   - BlogCategoryServicesImpl: `categories` cache'i ile tüm kategori listesi önbelleğe alınır.
   - TagServiceImpl: `tags` cache'i ile etiket listeleri ve tekil etiket sorguları önbelleklenir.
2) @CacheEvict:
   - Yeni kategori/etiket eklendiğinde, güncellendiğinde veya silindiğinde önbellek otomatik temizlenir.
3) TTL (Time To Live):
   - Kategoriler ve etiketler için varsayılan TTL: 30 dakika.
   - Genel veri önbelleği için TTL: 10 dakika.
4) Akıllı Fallback Desteği:
   - Docker / Redis bulunmadığında (`spring.cache.type=simple`) uygulama çökmez; Spring'in in-memory `ConcurrentMapCacheManager` yapısına otomatik geçiş yapar.


5. FLYWAY VERİTABANI MİGRASYON YÖNETİMİ (Adım 11):
--------------------------------------------------------------------------------
Kurumsal üretim sistemlerinde `hibernate.ddl-auto=update` veri bozulmasına ve kontrolsüz
şema değişikliklerine yol açabileceğinden, veritabanı şema yönetimi Flyway ile versiyonlanmıştır:

- V1__init_schema.sql:
  * users, roles, user_roles, blog_categories, blogs, comments, tags, blog_tags tabloları.
  * ANSI SQL uyumlu `GENERATED BY DEFAULT AS IDENTITY` ve ilişkisel Foreign Key Cascade kuralları.
- V2__seed_roles_and_categories.sql:
  * Başlangıç rolleri (ROLE_USER, ROLE_ADMIN, ROLE_SUPER_ADMIN).
  * Temel kategoriler (Yazılım Mimarisi, Bulut ve DevOps, Siber Güvenlik) ve etiketler.
- V3__add_performance_indexes.sql:
  * Foreign key ve sık sorgulanan alanlarda B-Tree performans indeksleri:
    `idx_blogs_category`, `idx_blogs_author`, `idx_comments_blog`, `idx_comments_user`,
    `idx_users_username`, `idx_users_email`, `idx_tags_name`, `idx_blogs_header`.
- Hibernate ile Entegrasyon:
  * PostgreSQL üretim profilinde `spring.jpa.hibernate.ddl-auto=validate` olarak ayarlanır.
  * Tabloları Flyway oluşturur; Hibernate sadece Java sınıfları ile şemanın uyumunu doğrular.


6. SOFT DELETE & GERİ YÜKLEME (RESTORE) MİMARİSİ (Adım 12):
--------------------------------------------------------------------------------
Kurumsal seviyedeki sistemlerde veri kaybını önlemek, hukuki/denetim uyumluluğunu
sağlamak ve kazara silinen verileri kurtarabilmek için "Soft Delete" (Mantıksal Silme)
deseni uygulanmıştır:

1) Veritabanı Desteği (V4__add_soft_delete_support.sql):
   - `blogs` ve `comments` tablolarına `is_deleted` (BOOLEAN, default FALSE) ve `deleted_at` (TIMESTAMP) eklendi.
   - Sorgu performansını korumak için `idx_blogs_is_deleted` ve `idx_comments_is_deleted` B-Tree indeksleri oluşturuldu.

2) Hibernate 6 Dekoratörleri:
   - `@SQLDelete(sql = "UPDATE blogs SET is_deleted = true, deleted_at = CURRENT_TIMESTAMP WHERE blog_id = ?")`:
     Standart `repository.delete(entity)` veya `deleteById(id)` çağrıldığında fiziksel DELETE yerine
     otomatik olarak soft delete UPDATE SQL'i çalıştırılır.
   - `@SQLRestriction("is_deleted = false")`:
     Tüm `findAll`, `findById`, JOIN ve ilişkisel sorgularda Hibernate otomatik olarak `WHERE is_deleted = false`
     filtresini sorguya enjekte eder. Silinmiş kayıtlar normal kullanıcı sorgularında asla listelenmez.

3) Geri Yükleme (Restore) ve Çöp Kutusu (Trash Bin):
   - Native SQL query ile `UPDATE ... SET is_deleted = false, deleted_at = NULL WHERE ...` restore mekanizması.
   - Sadece `ADMIN` ve `SUPER_ADMIN` rollerinin erişebildiği silinmiş kayıtları listeleme ve kurtarma API'leri:
     * `GET /blog/api/v1.0.0/deleted` (Silinmiş bloglar)
     * `PUT /blog/api/v1.0.0/restore/{id}` (Blog geri yükleme)
     * `GET /blog/api/v1.0.0/comments/deleted` (Silinmiş yorumlar)
     * `PUT /blog/api/v1.0.0/comments/{id}/restore` (Yorum geri yükleme)


7. NASIL ÇALIŞTIRILIR?
--------------------------------------------------------------------------------

Seçenek 1: Docker Compose ile Tam Sistem (PostgreSQL + Redis + Prometheus + Grafana + Backend)
```sh
# 1) Her şeyi arka planda inşa et ve başlat
docker compose up -d --build

# 2) Logları canlı incele
docker compose logs -f

# 3) Prometheus ve Grafana Erişimleri:
#    - Prometheus Web Arayüzü: http://localhost:9090
#    - Grafana Dashboard:      http://localhost:3001 (Kullanıcı: admin / Şifre: admin)
#    - Spring Actuator Metrik: http://localhost:5555/actuator/prometheus

# 4) Kapat
docker compose down
```

Seçenek 2: Sadece Veritabanı ve Redis'i Docker'da Başlatıp, Uygulamayı IDE'de Çalıştırma
```sh
# 1) Postgres ve Redis servislerini başlat
docker compose up -d postgres redis

# 2) Uygulamayı PostgreSQL profili ile çalıştır
mvn spring-boot:run -Dspring-boot.run.profiles=postgres
```

Seçenek 3: Docker Olmadan Hızlı Test (H2 + In-Memory Cache)
```sh
# Doğrudan çalıştır (varsayılan profil dev/H2'dir)
mvn spring-boot:run
```
